# Decision surface: which component, which precision, which QP

Generated by `scripts/visualize_decision.py` from the tracked per-precision surfaces only
(`{fmt}/results/summary.csv`, `{fmt}/results/configs_<fmt>.csv`, `artifacts/component_inventory.json`).
No raw ledger is needed, so every figure reproduces from a clean checkout.

```powershell
.\venv\Scripts\python.exe quantization-pluse-mse\scripts\visualize_decision.py
```

Metric definitions: `penalty` is the rate-equivalent cost from `pipeline.py export`,
`100 * ((1 + d_bpp/100) * 2^(-d_psnr/slope) - 1)`, using the local RD slope per dataset and QP.
Every figure uses the worst value across Kodak and CLIC and across the 8 QPs, i.e. a conservative
per-component verdict. Thresholds: green `<= 1%`, yellow `1-3%`, red `> 3%`.

## Findings

**1. The risk is concentrated in small components.** The three red components (H3 38.15%,
H0 10.09%, D5 8.06%) together hold 3.8% of parameters and 3.0% of kMAC/px. The four large
encoder blocks E1-E4 hold 84.7% of parameters between them and sit at 0.43-1.35% INT8 penalty.
So the model can be compressed where it matters: the bytes are in the safe region.

**2. Thirteen of nineteen components are green at INT8**, covering 70.4% of parameters and
70.8% of kMAC/px. The safe-level assignment costs 17.90 MB against 54.69 MB FP32 (-67.3%).

**3. Sensitivity is QP-dependent in both directions.** Encoder and decoder damage grows with QP
(E0 0.154% -> 1.174%, 7.6x; E1 0.258% -> 1.352%, 5.2x). Entropy damage shrinks (H3 38.152% ->
2.768%, 13.8x; H0 10.087% -> 1.308%, 7.7x). "H3 is red" is a QP0 verdict; at QP7 it is
near-green. This is the argument for a per-QP assignment `x[c,p,q]` over a shared `x[c,p]`.

**4. FP8 does not buy anything over INT8 here.** FP8-E4M3 is already per-output-channel scaled
(`core.py:84-87,105`) and still costs 14.8% on E1 against INT8's 1.35%. Three mantissa bits lose
to eight uniform bits. FP8-E5M2 is worse still (30.2%). Only FP16/BF16 are worth using as the
"safe" alternative to INT8 on fragile encoder blocks.

**5. The 4-bit columns are a lower bound, not a verdict.** INT4 and FP4 use per-output-channel
scaling only; group/block scaling (MXFP4, NVFP4) is not implemented. INT4 on H3 reads 163,482%,
which is a per-channel-scaling artifact, not a statement about 4-bit quantization in general.

## QAT / greedy / ILP: the decision

**QAT: skip, and say why.** The project rule is "QAT only if a component holding >= 5% of MACs
or parameters is red at INT8". No component meets it. The only large fragile component is E1
(yellow at 1.35%, 21.2% of parameters), and BF16 already costs it 0.015%. Paying for a
fine-tuning run to reach INT8 on E1 buys nothing that BF16 does not already give. Record the
skip as a measured decision, and revisit only if a red component grows past 5%.

**Greedy: keep it as the baseline.** At a 1% budget the greedy path with the weakest sensible
constraint yields 24.56 MB (-55.1%). It is order-dependent and cannot carry extra constraints.

**ILP: done, and it wins.** The problem is 19 components x 8 precision options = 152 binaries.
Because PULSE ships one weight file for all eight QPs, the variables are `x[component, precision]`
and the quality constraint is enforced at every QP, so the binding constraint is the worst-QP
total rather than the sum of per-component worst cases. Solved with HiGHS through
`scipy.optimize.milp` (already installed; OR-Tools was not needed).

| Budget | ILP size | Greedy size | ILP worst-QP predicted |
|---:|---:|---:|---:|
| 0.25% | 27.140 MB | 27.274 MB | 0.249% |
| 0.50% | 24.546 MB | 24.546 MB | 0.462% |
| 1.00% | **21.677 MB** | 21.677 MB | 0.972% |
| 2.00% | 18.389 MB | 18.389 MB | 1.986% |
| 3.00% | **17.885 MB** | 18.071 MB | 3.000% |

At the 1% budget the ILP reaches 60.4% size reduction. Greedy matches it at two budgets and
loses at the extremes; the honest conclusion is that this instance is easy for greedy, and the
ILP's value is the guarantee plus room for constraints greedy cannot express (memory, a
per-component floor, an uneven quality requirement).

## The additivity gate: passed

Every number on this page is an additive prediction, the sum of single-component penalties.
That assumption was tested with `scripts/analyze_additivity.py` against whole-model runs on
Kodak and CLIC at all 8 QPs.

| Config | Measured / predicted, Kodak | Measured / predicted, CLIC |
|---|---|---|
| uniform INT8 | 0.96 - 1.05 | 1.02 - 1.11 |
| safe mixed | 0.75 - 0.95 | 0.92 - 1.00 |
| greedy mixed | 0.73 - 1.66 (values under 0.4%) | 0.88 - 1.36 (values under 0.4%) |

Additivity holds within about 5% for uniform INT8, which is the case that matters, and the
prediction is slightly conservative on Kodak and slightly optimistic on CLIC. The summed
coefficients are therefore a valid input to the solver, and no coefficient has to be re-measured
before use. Ratios for BF16 are meaningless because both sides are near zero.
